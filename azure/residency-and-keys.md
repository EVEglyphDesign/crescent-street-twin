# Residency and Key Management — How Canadian Residency Is Actually Enforced

This document is the honest accounting the hard constraints demand: "all data resident in Canada... nothing replicating to a US region" and "customer-managed keys so the operator cannot unilaterally decrypt." It states plainly, per mechanism, what is real enforcement versus what is a claim Azure lets you make but cannot fully back. See `architecture.md` for the service choices this document justifies at the residency/key level.

## 1. Region pinning

Every resource in this design that stores or processes personal data is created with an explicit `location` parameter set to `canadacentral` (or, for the GRS replica, the automatically-paired `canadaeast` — see §3). This is a per-resource configuration choice, not a platform default — Azure will happily create resources in any region you tell it to, so region pinning is only as good as the discipline (and the policy guardrail in §2) behind it. Canada Central has three availability zones; Canada East has none and exists as the paired region — [Microsoft Learn: List of Azure regions](https://learn.microsoft.com/en-us/azure/reliability/regions-list); zone-count detail corroborated by [azurespeed.com: Canada Central region info](https://www.azurespeed.com/Information/AzureRegions/CanadaCentral). Canada Central's physical location is Toronto; Canada East's is Quebec City — same Microsoft Learn source.

## 2. Azure Policy: denying non-Canadian regions

Azure ships a built-in policy definition, **"Allowed locations,"** that restricts which regions resources can be deployed into, with configurable effect — `Audit`, `Deny`, or `Disabled` — [Microsoft Learn: List of built-in policy definitions – Azure Policy](https://learn.microsoft.com/en-us/azure/governance/policy/samples/built-in-policies). The Bicep template in `iac/main.bicep` assigns this policy at the resource-group scope with effect `Deny` and an allowed-locations list of `canadacentral` and `canadaeast` only.

**Two documented exclusions in this policy that matter here, stated plainly rather than glossed over:**

- The policy explicitly **excludes resource groups themselves** and any resource using the special **`global`** region value. A resource group's own metadata (its name, tags, and the fact that it exists) is control-plane metadata held in Azure Resource Manager, which is inherently non-regional — no Allowed-locations policy can pin that away. This is Azure's control plane, not this application's data plane; it holds no venue/user/consent/media content.
- The same built-in policy definition documentation lists **`Microsoft.AzureActiveDirectory/b2cDirectories`** as excluded — meaning this policy mechanism was never designed to constrain identity-directory resources like Entra ID/Entra External ID tenants. This is not a bug in the policy; it reflects that those services are non-regional by design (see §4). **You cannot policy your way to Canada-only identity — the exclusion is explicit and permanent, not a gap to be closed by better policy authoring.**

Recommended scope: assign at the **subscription** level (or a dedicated management group if the venue infrastructure ever grows beyond one subscription), not just the resource group, so that no future resource — including ones a future contributor creates outside this Bicep template — can silently land outside Canada.

## 3. Geo-replication settings — what must be off, and the one that's actually fine

- **Storage account GRS/RA-GRS/GZRS to a *chosen* secondary region:** not applicable here — GRS's secondary is not a choice at all. It is fixed to the storage account's **paired region**, and Microsoft's own worked example for this exact scenario reads: "an Azure solution can use Azure Storage in the Canada Central region with GRS storage to replicate data to the paired region, Canada East" — [Microsoft Learn: Azure region pairs and nonpaired regions](https://learn.microsoft.com/en-us/azure/reliability/regions-paired). The secondary region **cannot be changed after account creation** — [Microsoft Learn: Data redundancy in Azure Storage](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy). Net effect: turning GRS **on** for the storage accounts in this design is safe and Canada-only by construction — this is one setting that does not need to be turned off, unlike almost everything else in this section.
- **Front Door / Azure CDN:** must be left **off** for any endpoint serving personal data. Front Door is architecturally a global anycast edge service, "not tied to any specific Azure region" — it is one of the services Microsoft's own EU Data Boundary documentation lists as **structurally excluded** from regional data-residency guarantees, for the same reason it would be excluded from a Canada-only guarantee — [Microsoft Learn: Services excluded from the EU Data Boundary](https://learn.microsoft.com/en-us/privacy/eudb/eu-data-boundary-excluded-services); general caveat at [Azure Data Residency](https://azure.microsoft.com/en-us/explore/global-infrastructure/data-residency). `architecture.md` §1.1 already rejects Front Door for this reason for the *public* static site too, to keep the "nothing leaves Canada" claim simple to audit — there is exactly one edge case (the public, non-personal site) where using it would arguably be safe, and this design still declines it.
- **Cosmos DB multi-region writes / "Add region":** must be left **off** (single-region account, Canada Central only). Cosmos DB serverless accounts can only run in a single region anyway — [Microsoft Learn: Serverless (consumption-based) account type](https://learn.microsoft.com/en-us/azure/cosmos-db/serverless) — so this is enforced by the capacity-mode choice itself, not just a setting someone could accidentally flip. If this project ever moves off serverless to provisioned throughput for cost reasons, this setting becomes something a human must actively avoid rather than something the platform prevents.
- **Key Vault Managed HSM multi-region replication:** not applicable in this design because Managed HSM was rejected on cost grounds (`architecture.md` §1.8), but worth recording regardless: Canada Central and Canada East are explicitly listed as regions that **"cannot be extended regions at this time"** for Managed HSM replication — [Microsoft Learn: Enable multi-region replication on Azure Key Vault Managed HSM](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/multi-region-replication). Had Managed HSM been chosen, there would be no supported way to get an in-country DR replica of the HSM pool between the two Canadian regions at all.

## 4. Hidden cross-region dependencies: identity, control plane, and telemetry

This is the section to read most carefully — it is where "designed for Canadian residency" and "actually, fully Canadian residency" diverge.

### 4.1 Identity — the genuine, currently-unresolved gap

**Microsoft Entra ID and Microsoft Entra External ID are non-regional services.** Tenant creation asks you to pick a "Country/Region," but this setting maps to a broad multi-country **geo**, not an exclusive in-country residency boundary. Canada's setting maps into the **"North America" geo, which is shared with United States datacenters** — [Microsoft Learn: Microsoft Entra ID and data residency](https://learn.microsoft.com/en-us/entra/fundamentals/data-residency). This is confirmed specifically for Canada in a Microsoft Q&A thread: "Microsoft Entra ID... are Non-regional services... your Entra ID tenant would show up US datacenter as location" — [Microsoft Q&A: Canada only Geo for Entra ID?](https://learn.microsoft.com/en-us/answers/questions/1515933/canada-only-geo-for-entra-id). The **"Go-Local"** add-on, which does provide genuine in-country residency for identity data on Entra ID, is currently available **only for Australia and Japan** — not Canada — per the same Microsoft Learn residency page.

**Consequence, stated without softening:** sign-in credentials, and whatever minimal profile data Entra External ID itself stores (email, phone, display name, authentication logs), are **not guaranteed to stay in Canada** under this design, using currently-available Azure identity products. This directly and literally conflicts with the hard constraint "nothing replicating to a US region" if read to include identity data.

**Mitigation adopted (not a fix — a scope-reduction):** keep the Entra directory holding only account credentials and the minimum linkage needed to associate a user with their Cosmos DB / Blob-stored records (an opaque object ID). Location, consent grants, media, and presence data — the parts of this project that are actually sensitive — are stored exclusively in the Canada-Central-pinned Cosmos DB and Blob Storage services described in `architecture.md`, which *are* fully region-pinnable and policy-enforceable. The non-regional exposure is thereby narrowed to "this platform knows someone with this email signed up," not "this platform knows where someone was or what they photographed."

**What a fully compliant alternative would require:** either (a) Microsoft extending Go-Local to Canada, (b) a fully custom, self-hosted identity system running only in Canada Central (rejected in `architecture.md` §1.7 / `decisions.md` ADR-8 on security-posture grounds), or (c) a third-party CIAM vendor with an explicit Canada-only data-residency guarantee (not evaluated in this pass — flagged as future work, not ruled out).

### 4.2 Azure control plane / ARM metadata

Every Azure resource, regardless of region, has metadata (resource IDs, tags, deployment history, RBAC role assignments) held in Azure Resource Manager, which is a global control-plane service by design. This is standard across all of Azure and all regions — it is not specific to this project's choices, and there is no Azure region setting that changes it. It holds structural/administrative metadata about the *existence and configuration* of resources, not the application data (consent grants, media, location, ledger entries) that lives inside them. This is disclosed for completeness, not treated as a residency violation of the same order as §4.1 — no competitive-grade attacker learns a user's location or a venue's revenue from ARM metadata.

### 4.3 Telemetry and diagnostics

Azure Monitor / Log Analytics workspaces are themselves region-pinnable (this design pins the workspace to Canada Central — `architecture.md` §1.9), so *first-party* application diagnostic data stays in Canada if diagnostic settings are correctly scoped, which is the entire purpose of the `DeployIfNotExists`-based policy initiative referenced in `architecture.md` §1.9 and encoded (as a placeholder) in `iac/main.bicep`. However, some **platform-level telemetry Microsoft collects about its own services' health and usage** (not this application's data) may be processed centrally regardless of resource region — this is standard across every Azure customer and is not something a subscription-level Azure Policy assignment can change, because it is Microsoft's own operational telemetry about the service, not customer data stored in the resource. This is noted here for honesty; it is a property of using any public cloud platform, not a design flaw specific to this architecture.

## 5. Customer-managed keys: Key Vault Premium vs. Managed HSM

- **Chosen: Azure Key Vault, Premium tier**, HSM-backed keys, Canada Central, used as customer-managed keys (CMK) for Storage account and Cosmos DB encryption-at-rest. Approximate pricing: $1/key/month for RSA 2048-bit HSM-backed keys, plus $0.03 per 10,000 cryptographic operations; advanced key types (RSA 3072/4096, elliptic curve) are tiered from about $5/key/month (first 250 keys) down to $0.40/key/month at higher volume — [Azure Key Vault pricing](https://azure.microsoft.com/en-us/pricing/details/key-vault/), corroborated by [pump.co: Azure Key Vault Pricing guide](https://www.pump.co/blog/azure-key-vault-pricing/).
- **Rejected: Managed HSM.** A Standard B1 pool runs approximately $3.20/hour — **roughly $2,300–2,400 per month** — billed continuously from provisioning regardless of actual use — [Azure Citadel: Customer Managed Keys for Encryption at Rest](https://www.azurecitadel.com/blog/2026-05-05-cmk-l2-encryption-at-rest/) and [Microsoft Q&A: Managed HSM AES keys pricing](https://learn.microsoft.com/en-us/answers/questions/1031620/managed-hsm-aes-keys-pricing). Even a deleted-but-not-yet-purged Managed HSM instance continues billing during its mandatory soft-delete retention window per the same sources. At six-to-sixty-venue scale, this cost is disproportionate by roughly two orders of magnitude relative to the actual key-management workload. See §3 above for the additional finding that Canada Central and Canada East cannot cross-replicate a Managed HSM pool today regardless of cost.
- **Purge protection:** enabled on the Key Vault (see `iac/main.bicep`) — this prevents even a subscription Owner from permanently deleting the vault (and therefore the CMK keys) during the soft-delete retention window, which is a meaningful operator-side self-restraint control, not just a Microsoft-side one.
- **Key rotation:** Key Vault supports configurable automatic rotation policies per key (e.g., rotate every 12 months, or on a shorter cycle for higher-sensitivity keys). Recommendation for this design: a 12-month rotation policy on the CMK keys protecting Cosmos DB and Blob Storage, matching the 12-month consent-expiry cycle already built into the consent register — not because they must align, but because it gives the operator one recurring "review the whole system" cadence instead of two.

## 6. What the operator genuinely cannot decrypt, versus what is theatre

This is the section the hard constraint "customer-managed keys so the operator cannot unilaterally decrypt" actually demands an honest answer to.

**Genuinely enforced by CMK + Key Vault RBAC:**
- Data at rest in the Cosmos DB consent register and the Blob Storage media/ledger containers is encrypted with keys held in Key Vault, not keys Microsoft manages transparently on the operator's behalf. If the operator's own Azure RBAC role does not include Key Vault key-access permissions (`Key Vault Crypto User`/equivalent, scoped narrowly, ideally to a managed identity used only by the Functions app — not to the human operator's own account), then a human operator with, say, only Storage-level "Reader" access **cannot** decrypt that data by reading the raw storage — they would need to separately compromise or be granted access to the Key Vault key, which is a distinct, auditable, revocable permission. This is real: revoking the Function app's managed-identity access to the key, or disabling the key itself, functionally cuts off decryption for anyone using the normal access path, including the operator, without a separate Key Vault-level grant.
- Purge protection means the operator cannot unilaterally destroy the key material either, even if they wanted to erase the evidence of having done so — a real constraint on operator behavior, not just attacker behavior.

**Theatre, or at least partial theatre — stated honestly rather than left implied:**
- **Anyone with subscription Owner or Key Vault Administrator rights can grant themselves Key Vault access at any time.** CMK protects against *casual* or *unauthorized* operator access and against a compromised lower-privilege credential — it does not protect against the actual highest-privilege operator (the subscription owner) simply elevating their own permissions, because Azure RBAC is itself controlled from within the same subscription. A genuinely adversarial-operator threat model would require a governance control *outside* Azure entirely (e.g., a break-glass process requiring sign-off from a second party who holds a separate credential, or a Key Vault access policy requiring multi-party approval) — this design does not implement that; it is flagged here as a gap, not solved.
- **Microsoft, as the underlying platform provider, retains the ability to access the physical infrastructure** that hosts both the encrypted data and (for Key Vault Premium, as opposed to a customer-held offline HSM) the key material itself. CMK with Key Vault raises the bar against the *operator* and against unauthorized *third parties*; it does not remove Microsoft from the trust boundary, because Key Vault Premium's HSM is a *Microsoft-managed, multi-tenant* HSM service, not hardware the operator physically possesses. A fully "Microsoft cannot decrypt this either" posture would require Managed HSM with a customer-controlled security domain and careful key-release policies — even then, Microsoft's infrastructure still executes the cryptographic operations. This project's threat model — protecting participants' consent, location, and photo data from casual operator misuse or a compromised low-privilege credential — is well served by Key Vault Premium CMK. A threat model that must exclude Microsoft itself is not achievable within Azure at any price point in this design, and should be stated to venues and users as such rather than oversold.
- **Diagnostic logs and ARM metadata (see §4.2–4.3) are not CMK-encrypted with the same per-resource keys** in this design as a baseline (CMK for Log Analytics is possible but was not assumed by default — see `architecture.md` §3 data-flow table) — meaning some operational metadata about *when* things happened and *which resource* was touched is more accessible to a standard operator role than the underlying consent/location/media content itself. This is a reasonable trade for operability (you need to be able to debug something without re-provisioning key access every time) but should not be described to venues as "everything is CMK-protected" without this caveat.

**Bottom line for venue- and user-facing communication:** say "customer-managed keys mean the operator's normal day-to-day access cannot read your location, photos, or consent records without a separate, auditable, revocable Key Vault permission grant." Do not say "not even the operator can ever access your data" — that claim is not true of Key Vault Premium (or, arguably, of any managed-HSM offering where Azure RBAC ultimately governs access), and overstating it would be a disclosure problem waiting to surface later.
